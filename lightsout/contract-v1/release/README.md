# MFENX Local v2 release-authenticity bundle

This directory adds a signed identity-and-supply-chain layer to the existing
sealed release evidence. It does not modify the evidence bundle.

The signed subject is the accepted `mfenx-local` binary with SHA-256:

```text
a1043e568704163b9dedf536c5feb60b0b7fd23097a2a8f0504d55d7ddcb1e3c
```

The bundle contains:

- a detached, domain-separated Ed25519 signature over the release manifest;
- the public key and an OpenSSH `allowed_signers` policy;
- a CycloneDX 1.5 dependency SBOM;
- a post-hoc in-toto/SLSA provenance statement;
- a signed local reproduction record derived from the sealed acceptance run;
- scripts that verify the complete chain and recreate the SBOM.

## Verify

From the repository root:

```bash
release/mfenx-local-v2-20260821-a1/verify-release.sh
```

Expected result:

```text
MFENX Local v2 signed release verification PASS
release key: SHA256:Uhj/Ci2+3KA2JN/H8+Sl6nhAiTeD76zvajqvxLOYTTc
```

The script first verifies the signature under the `mfenx-release` namespace,
then enforces the manifest encoding profile, hashes every listed artifact,
checks every file in the 1,307-entry sealed evidence inventory, and validates
the core SBOM, provenance, and reproduction bindings.

The release-key fingerprint must be obtained through an independent trusted
channel before the first verification. A public key shipped beside a signature
cannot, by itself, prove who controls that key.

## What the signature proves

After the fingerprint is independently pinned, a valid signature proves that
the same release key approved the exact manifest bytes. The manifest binds the
accepted binary, frozen source inventory, sealed evidence inventory,
acceptance result, SBOM, provenance, and reproduction record by SHA-256 and
byte length.

It does not prove that the implementation is secure, that the measurements
generalize, that the build was independently reproduced, or that the key owner
has been certified by a third party. The key was created locally for MFENX on
2026-08-21. It is not hardware-backed and has not been published in a
transparency log. Treat it as a project-continuity key until it is certified
through a separately controlled identity and moved to stronger custody.

The private key is outside the workspace under the operator's private data
directory. No private-key bytes or credentials are present in this bundle.

## Manifest encoding profile

`RELEASE-MANIFEST.canonical.json` uses the MFENX JSON profile v1, not RFC 8785
JCS. The profile permits objects, arrays, UTF-8 strings, booleans, null, and
integers only. It is serialized by jq 1.8.1 using `jq -cS .` and ends with one
LF byte. Verification regenerates those bytes and requires an exact match.

Because this release manifest has no floating-point values and only ASCII
member names and string data, this small profile is sufficient for the current
artifact. A future format must change the schema identifier before expanding
the permitted data model or serializer.

## SBOM scope

`mfenx-local-v2.sbom.cdx.json` is a CycloneDX 1.5 build-dependency SBOM
generated by cargo-cyclonedx 0.5.9 from the locked Rust metadata for
`rarecomp-mfenx-local` on `x86_64-unknown-linux-gnu`.

Its root component is the application package. Its dependency closure contains
46 components: 44 registry crates and the 2 local path crates
`rarecomp-mfenx-ir` and `rarecomp-mfenx-tensor-store`. The closure includes
normal and build dependencies resolved for that target. It excludes dev-only
dependencies, unrelated workspace members, source-file inventory, runtime
data, and operating-system libraries. This is therefore not a binary-composition
scan. The sealed evidence separately records the accepted ELF dynamic-library
and dependency inspection.

Recreate the exact normalized SBOM with:

```bash
release/mfenx-local-v2-20260821-a1/recreate-sbom.sh
```

The script works in a disposable workspace copy because cargo-cyclonedx
expands a member manifest to its containing workspace. Only the scoped local
executor SBOM is selected; generated SBOMs for other members never enter the
source tree. Reproduction requires the locked sources, cargo-cyclonedx 0.5.9,
jq 1.8.1-compatible serialization, and the recorded source-date epoch.

## Provenance qualification

`mfenx-local-v2.provenance.intoto.json` uses the in-toto Statement v1 envelope
and SLSA provenance v1 predicate shape. It was assembled after the build from
the sealed evidence. It was not emitted natively by an isolated build service,
and this release makes no SLSA build-level claim.

The statement binds the binary to the frozen source inventory, `Cargo.lock`,
root manifest, toolchain file, exact offline build command, accepted evidence,
and SBOM. Build start and finish fields are deliberately absent: the harness's
structured `compile` timing measures MFENX image compilation, not the Rust
binary build. Filesystem timestamps bracket the recorded Rust build, but they
are not treated as cryptographic event attestations.

## Reproduction qualification

`local-reproduction-record.json` preserves the current green acceptance run.
It records one local machine, one workload, and one accepted release run. It is
not one of the unrelated-machine reproductions required by the next phase, and
its performance value must not be generalized beyond its recorded conditions.

The release manifest signature covers this record and the immutable evidence
that supports it.
